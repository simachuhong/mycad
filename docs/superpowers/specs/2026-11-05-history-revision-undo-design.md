# 历史修订撤销设计草案

状态：运行期操作撤销已接入 Bus 与 GUI；专项回归及剩余人工验收范围见 [U11 证据](../../../.omo/evidence/ui-redesign/u11-baseline.md)。原命令级 API 仍保留。

U11 需要一次撤销已确认的历史改参或“改参并重选失效面”。当前 `CommandBus.undo(n)` 只删除末尾 `n` 条命令，`amendments` 则记录仍存在于模型历史的参数修订；因此它不能撤销一次修订。ADR-001、ADR-008 和 E3 设计锁定了此行为，不可仅在 GUI 将现有撤销改名或声称复合候选可一步撤销。

## 候选方案

增加 Bus 所有的、版本标记为 1 的**运行期操作历史**，以事务为单位记录足以恢复确认前后可重放命令状态的数据。普通命令、批事务、修订、复合候选、追加以及撤销/重做必须共用同一先后顺序；UI 的 Ctrl+Z/Ctrl+Y 走新的操作接口，既有 `undo(n)`/`redo(n)` 命令级 API 和 CLI 契约保持不变。草图本地草稿继续优先处理其自身撤销。

恢复由 Bus 在事务内替换命令状态并全量重放，不能写入几何快照或绕过 Bus。历史修订撤销应恢复确认前参数和相应的 amendment 列表；重做恢复确认后的同一组参数、审计字段和身份，不重新生成时间戳。复合修复一次撤销/重做作为一个操作，失败整体回滚，发布的模型事件、revision 和候选失效规则必须与普通提交一致。

操作历史是运行期状态，不写入现有 `.mc.json`，保存或重开不暗示可跨进程撤销修订。文档重开后的旧命令仍可按现有命令级规则撤销，UI 必须清晰区分能力。保存不应清空当前会话的操作历史；另存、切文档和关闭须隔离历史与失效候选。

## 必须解决的边界

- 首次身份/档案升级与复合提交：撤销内容时不降级档案；命令身份、已存在 redo 命令身份、下游引用及重做后的身份必须一致。
- 不能只记录修订操作而漏掉随后执行的普通命令，否则 Ctrl+Z 会错序；直接调用旧 API、插件、CLI、计划执行和批事务时也必须一致地记录或显式使新历史失效，不能悄悄跳过操作。
- 原有 `undo(n)` 可从已重开的完整历史撤销命令；新操作历史的起点、跨起点继续撤销和两套 redo 的衔接必须定义并测试。历史被外部操作改变后应拒绝过期恢复，而非猜测。
- 恢复失败或恢复本身失败时，维持既有快照回滚及 unhealthy 语义；错误不能留下部分命令、几何、审计、dirty、版本或 redo。
- 内存占用需要上限；达到上限后不得影响命令历史可重放或错误地允许跨边界 redo。不得把此运行期栈描述成不可篡改审计日志。
- 二维图层和草稿边界、异步任务完成后的撤销路由、工程图依赖更新、候选授权失效，以及文档切换/保存/重开均须回归。

## 实施门槛

先形成对 ADR-001 和 ADR-008 的明确增补，给出旧 API 与 UI 新接口的兼容契约；再以失败测试覆盖单修订、复合修复、身份升级、混合命令顺序、跨起点、旧 API 混用、失败注入、文档隔离和保存重开。只有以上行为及 scoped 回归通过后才可将 U11 的修订撤销标为完成。
