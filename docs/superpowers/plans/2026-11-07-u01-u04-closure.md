## 2026-11-07 write-failure investigation

Two independently reproduced failures remain: a failed write after draft preparation loses (1) the draft redo branch and (2) a document redo operation that existed before preparation. Both are strict expected failures in `tests/ui/test_close_cancel_state.py`; the second raises `InvalidHistoryError` when redo is attempted.

The preparation callback commits into the live Bus before `save_document` attempts its atomic file replacement. Committing clears both runtime operation redo and draft redo. Undoing the new command alone does not restore either prior redo branch; mixed edits can commit multiple commands and can upgrade the archive version. Saving a replay candidate first also needs a protocol for failure between candidate commit and file replacement.

The remaining implementation needs a transaction with the following acceptance conditions:

- Retain the original draft, including undo/redo, selection, constraints, layers, mixed-edit timeline and source binding, until its write succeeds.
- Preserve the Bus document state, archive version, dirty state and both command-level and operation-level undo/redo histories on failure; geometry must match replay and revision values must not move backwards.
- Roll back only unsaved entries in a partially successful Save All operation; successful files and their session ownership must remain intact.
- Detect source revision or session changes before restoration and refuse to overwrite newer work; report restoration failures explicitly.
- Preserve document and file identities, audit data, referenced source semantics, and the existing Bus-only mutation boundary.
- Verify ordinary and mixed drafts, prior document redo, Save As, partial Save All, failed preparation, stale source, atomic file failure, successful save, and save/reopen/undo. Include scoped layering, Ruff, format and basedpyright checks.

No transaction implementation has been selected or validated yet. A safe change must resolve the file-replacement versus live-commit failure window rather than assuming one of those steps cannot fail.

## Approved implementation: save checkpoints (2026-11-07)

The user approved the checkpoint approach and requested implementation and verification.

- The Bus owns opaque, single-use checkpoints for complete document state and both runtime history stacks. Recovery verifies the prepared revision, rebuilds geometry, preserves monotonic revisions, invalidates obsolete proposals, and marks the Bus unhealthy if rebuilding fails.
- The save-specific sketch submission retains its original editor until settlement. Recovery runs on the serialized worker. Mixed-edit history is rebound to the restored source revision only after successful Bus recovery; invalid transactions stay invalid.
- All paths are collected first. Documents are then prepared, written and settled one at a time in dependency order. Earlier successful saves remain saved; failed entries recover; later entries remain pending.
- Atomic file replacement is the commit boundary. Errors after the write are reported as saved with synchronization errors and never trigger document rollback. Changes during file notifications remain dirty.
- Existing expected-failure markers were removed. The failed-write test now requires the original draft and original document history after recovery.
- Preserve existing workspace changes and do not commit. Verification remains scoped to the save lifecycle, Bus/history and layering; physical desktop/GPU and user acceptance remain pending.
